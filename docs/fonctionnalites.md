# Fonctionnalités de l'application

Détail par onglet de ce qui existe réellement dans le code (à tenir à jour à chaque fonctionnalité ajoutée/retirée). Vue d'ensemble courte dans `README.md` ; ce fichier est le niveau de détail utile pour reprendre le développement.

L'app a 4 onglets, pilotés par un signal `vue` dans `HomeComponent` (`'liste' | 'carte' | 'favoris' | 'planning'`) — **pas de routing Angular**, tout est dans un seul composant + enfants.

## Liste (`home.component.ts/html`)

- Recherche texte (debounce 250ms) sur nom, quartier, description, commentaires, noms de plats.
- Filtre par type : chips Tout / Restaurants / Activités / Magasins. **Défaut : `'tout'`** (ce filtre est partagé avec la Carte — un défaut sur un seul type masquerait silencieusement les autres sur la carte).
- Filtre par quartier : picker custom en bottom-sheet (pas un `ion-select`, pour avoir des en-têtes de ville en gras/majuscules), quartiers groupés par ville. Recherche texte en tête du picker (`rechercheQuartier`/`quartiersParVilleFiltres()`, réinitialisée à chaque ouverture via `ouvrirPickerQuartier()`) pour retrouver un quartier sans dérouler toute la liste ; "Tous les quartiers" reste toujours visible, même en cours de recherche (c'est une action de reset, pas un résultat).
- Sous-filtres spécifiques au type actif : plat + catégorie (Plat/Snack) pour les restaurants, type de magasin pour les magasins.
- Filtre "Ouvert" (chip, orthogonal aux chips de type — combinable avec n'importe lequel, présent en vue à plat comme en vue groupée) : par défaut filtre sur "ouvert maintenant" (`l.estOuvert`, précalculé au chargement). Un `<input type="time">` apparaît à côté dès que le chip est actif pour projeter le filtre sur une heure choisie plutôt que l'instant présent (`HomeComponent.filtreHeureProjetee`/`onHeureProjeteeChange()` — recalcule `estOuvertMaintenant(l.horairesJson, momentProjete)` à la volée, sur le jour courant uniquement, pas un autre jour de la semaine) ; utile pour planifier à l'avance ("qu'est-ce qui sera ouvert à 19h ?"). Le chip affiche alors "Ouvert à HH:mm" au lieu de "Ouvert", et les cartes filtrées échangent leur badge Ouvert/Fermé "maintenant" (potentiellement trompeur ici) contre "Ouvert à HH:mm" ; le badge "Ferme dans X min" (qui n'a de sens qu'au présent) est masqué le temps que la projection est active. Désactiver le chip réinitialise l'heure projetée (repart de "maintenant" à la prochaine activation). Au clic sur l'input (`onClicHeureProjetee()`), les minutes sont forcées à "00" (seule l'heure ronde nous intéresse ici) et le segment heures est sélectionné via `.select()` pour taper directement par-dessus sans naviguer jusque-là — comportement de `.select()` sur un `<input type="time">` non standardisé mais observé sur Chromium/Firefox, seule API disponible pour cibler un segment précis.
- Bouton "regrouper" : bascule liste plate / groupée par Ville → Quartier.
- Regroupement par franchise dans la vue à plat (non groupée par quartier) : les lieux de même type dont le nom normalisé (insensible casse/accents) est identique — typiquement un konbini ou une chaîne présente dans plusieurs quartiers, voir la case "Franchise" d'Ajouter un lieu — sont fusionnés en une seule carte (emoji + nom + badge "N quartiers", `HomeComponent.lieuxAffichesGroupesFranchise`) plutôt que dispersés dans la liste. Repliée par défaut (`franchisesOuvertes`, un `Set` de clés — plusieurs franchises peuvent être dépliées en même temps indépendamment), un tap déplie la liste des quartiers de cette franchise ; chaque ligne quartier affiche l'Ouvert/Fermé et l'horaire du jour propres à cette antenne, et un tap dessus ouvre le détail habituel de ce lieu précis. Le groupe est positionné au rang de sa première occurrence dans la liste triée, pour ne pas perturber le tri distance/alphabétique. Ne s'applique qu'à la vue à plat : en mode groupé Ville → Quartier, les instances apparaissent déjà séparées sous leurs quartiers respectifs, ce qui est l'info recherchée dans ce mode.
- Tri : par distance si la position est connue, sinon alphabétique. Pas de sélecteur de tri manuel (retiré sur demande explicite : distance-ou-alphabétique suffit).
- Chaque carte de lieu affiche : emoji (heuristique par mot-clé, voir `utils/emoji-lieu.ts`), cœur si favori, icône crayon si une note perso existe, badge "Nouveau" (voir plus bas), badge Ouvert/Fermé, badge "Ferme dans X min" si pertinent, distance, prix, horaires du jour.
- Bouton "Voir sur la carte" (icône + label) dans l'en-tête de section, visible seulement si un quartier est filtré : bascule sur la Carte et la recentre/zoome sur les lieux de ce quartier (`CarteComponent.recentrerSurMarqueurs()`). Même intitulé que le bouton équivalent de la popup détail (voir plus bas), qui centre lui sur un lieu précis (`CarteComponent.centrerSurPoint()`).
- États : squelettes de chargement, message d'erreur + bouton Réessayer, état vide.
- Bouton flottant "retour en haut" (bas-droite, au-dessus de la tab bar) : apparaît une fois le défilement de `ion-content` passé un seuil (400px), masqué sinon. Écoute `(ionScroll)` sur `ion-content` (`[scrollEvents]="true"`), remonte via `IonContent.scrollToTop()`. Visible uniquement en vue Liste (pas Favoris/Planning).
- Badge "Nouveau" (`NouveauteService`, localStorage, 100% local à l'appareil — même principe que `FavorisService`/`NotesService`/`VusRecemmentService`) : affiché sur un lieu détecté pour la première fois sur cet appareil, pendant 7 jours. Pas de colonne "date d'ajout" dans le Sheet — l'horodatage est celui de la première fois où *cet appareil* a vu l'id, pas la date réelle d'ajout au Sheet. Au tout premier lancement de l'app (aucun historique local), tous les lieux connus à cet instant sont backdatés silencieusement pour ne pas afficher "Nouveau" partout ; seuls les lieux apparus après coup (rafraîchissements suivants) sont marqués.
- Section "Vus récemment" : en-tête repliable (repliée par défaut, signal `recentsOuvert` non persisté) qui révèle une rangée horizontale scrollable avec les derniers lieux dont la popup de détail a été ouverte (`VusRecemmentService`, localStorage, 100% local à l'appareil — même principe que `FavorisService`/`NotesService`). Visible avec n'importe quel filtre de type (Tout/Restaurants/Activités/Magasins), tant qu'aucune recherche/quartier/regroupement n'est actif pour ne pas se superposer à une liste déjà filtrée par l'utilisateur ; `lieuxRecents()` filtre elle-même les lieux par le type actif (sauf `'tout'`) pour rester cohérente avec la liste affichée en dessous. L'en-tête reste affiché même sans historique (état vide "Aucun lieu consulté récemment." une fois dépliée), plutôt que de disparaître entièrement — l'utilisateur sait ainsi que la fonctionnalité existe avant d'avoir consulté un premier lieu. Cliquer sur une vignette de cette section ouvre le détail sans rafraîchir sa date de dernière visite ni le faire remonter en tête (`ouvrirDetails(lieu, false)`), pour ne pas figer artificiellement l'ordre de l'historique.

### Popup de détail d'un lieu

Modale en bottom-sheet swipeable (`[breakpoints]="[0,1]"`), commune aux 3 types avec un template par type (`@if (detail.type === ...)`) :

- Badges : Ouvert/Fermé, "Ferme dans X min", "Réouvre à...", quartier (**cliquable** → ferme la popup, filtre la Liste sur ce quartier en mode Tout), prix, distance.
- Étoiles (moyenne `Avis`, 8 votants nommés dans le Sheet — pas de notation utilisateur, uniquement affichage).
- Horaires de la semaine, description, commentaires.
- Restaurant uniquement : liste de plats en chips colorées (vert = Plat, rouge = Snack), cliquables → popup détail du plat.
- Note personnelle : `ion-textarea` avec auto-save debounced (~600ms après la fin de la frappe, `HomeComponent.enregistrerNote()`/`flusherNote()`) + toast de confirmation. Un flush immédiat est forcé à la fermeture de la popup (bouton, swipe ou tap sur le fond) pour ne pas perdre une saisie récente si elle survient avant la fin du debounce.
- Bouton favori (cœur) avec toast de confirmation.
- Liens d'action : Partager (Web Share API si dispo — partage natif du système —, sinon repli sur copie presse-papiers du nom + lien Maps ; une annulation du partage par l'utilisateur n'affiche pas d'erreur), Voir sur la carte (interne à l'app, ferme la popup et centre `CarteComponent` sur ce lieu — visible si latitude/longitude connues), Maps (lien externe), Menu, Vidéo, Plus d'infos (selon ce qui est renseigné).
- Magasin : un seul quartier, comme Restaurant/Activité (voir pièges connus — `MagasinModel.Quartier` a longtemps été un tableau pour supporter une colonne "Quartier" à virgules, ce qui cassait le filtre par quartier de la Liste/Carte pour ces lignes).

## Carte (`components/carte/`)

- Leaflet + `leaflet.markercluster`, tuiles **raster** MapTiler (`streets-v2`) — pas de WebGL/vecteur (voir pièges connus : ça plantait sur la machine de dev).
- **Composant monté en permanence**, masqué en CSS (`visibility:hidden`) plutôt que détruit via `@if` — recréer le contexte carte à chaque changement d'onglet causait des "WebGL context was lost".
- Marqueur emoji par lieu, marqueur de position dédié, bouton recentrage sur la position.
- Filtre "favoris uniquement" (bouton cœur haut-droit) ; overlay d'état vide si le filtre ne retourne aucun marqueur.
- Gestion d'erreur d'init (clé MapTiler invalide, etc.) avec bouton Réessayer.
- Optimisation : signature (id+favori) mémoïsée pour éviter de reconstruire tous les marqueurs à chaque tick de géolocalisation.

## Favoris

- Simple filtre de `lieux()` par `FavorisService.estFavori(id)`, mêmes cartes/popup que la Liste.
- Badge de comptage sur le bouton de la tab bar (masqué si 0).
- Boutons Exporter/Importer (voir `exporterDonnees()`/`declencherImport()`/`onFichierImporte()`) : affichés uniquement dans l'en-tête de section de cette vue (pas dans l'en-tête global de l'app, ni sur la Liste) — ce sont des favoris/notes qu'on manipule, donc l'action n'a de sens que sur cet onglet.

## Planning (`components/planning/`)

- Source : onglet Sheet dédié (gid `1009205135`), service séparé avec son propre cache localStorage (`planning_cache`), stratégie stale-while-revalidate (affiche le cache immédiatement, revalide en réseau).
- Regroupement par jour ; jour courant mis en évidence (bordure + fond teinté + badge "Aujourd'hui") et **auto-scrollé** à l'ouverture de l'onglet (une fois par montage du composant).
- Bouton flottant "Aujourd'hui" (même emplacement/mécanisme que le "retour en haut" de la Liste, `HomeComponent.boutonAujourdhuiVisible()`/`allerAujourdhuiPlanning()`) : la mini-nav de jours en tête (avec le jour courant surligné) défile avec le reste du contenu et disparaît donc du viewport une fois qu'on a scrollé — ce bouton permet d'y revenir sans remonter toute la liste à la main. N'apparaît que si un des jours affichés est effectivement "aujourd'hui" (voyage pas commencé/déjà fini → pas de bouton).
- Filtre par ville : chips avec compteur d'activités par ville, apparaissent seulement si plusieurs villes existent dans le planning ; retour en haut de liste au changement de filtre.
- Lien vers la fiche lieu : chaque activité est comparée (nom normalisé, accents/casse ignorés) aux lieux connus (`lieuxParNom`) ; si ça matche, un chevron apparaît et le clic ouvre la popup détail habituelle.
- Détection de ville même quand la colonne "Ville" du Sheet est vide (cellules fusionnées côté Sheet) : voir `docs/architecture-et-pieges.md`.
- Bouton Réessayer sur erreur réseau (bandeau discret si des données en cache restent affichées, état vide dédié sinon).
- Le bouton de rafraîchissement de l'en-tête (commun à tous les onglets) délègue au chargement propre du Planning quand cet onglet est actif (`HomeComponent` a une `@ViewChild(PlanningComponent)`).
- **Météo du jour** (`MeteoService`) : badge emoji + min/max affiché dans l'en-tête de chaque groupe de jour, pour la ville de la **dernière** activité du jour (meilleure approximation d'où on passe la soirée, y compris un jour de trajet entre deux villes). Source : Open-Meteo (gratuit, sans clé API) — géocodage du nom de ville (`geocoding-api.open-meteo.com`) puis prévisions jusqu'à 16 jours (`api.open-meteo.com/v1/forecast`), résultat mis en cache 6h en localStorage par ville (clé `meteo_cache_<ville>`), indépendant du cache `SheetsApi`/`planning_cache`. Purement best-effort : ville non géolocalisable, jour hors de la fenêtre de prévision (~16 jours, donc rien pour un jour trop lointain) ou erreur réseau se traduisent silencieusement par l'absence du badge, jamais par une erreur affichée — la météo est cosmétique, pas une donnée du Sheet.
- **Hébergements** (`HebergementService`, onglet Sheet dédié "Hébergement") : bandeau dédié en tête de jour, distinct des activités, sur le jour d'arrivée ("🏨 Nom — check-in HH:mm") et sur le jour de départ ("check-out HH:mm"). Un hébergement n'apparaît que sur un jour qui existe déjà comme groupe dans le Planning (au moins une activité/un trajet ce jour-là) — limitation acceptée, pas de jour "vide" créé spécifiquement pour un hébergement. Contrairement au Planning lui-même (cache localStorage stale-while-revalidate), cet onglet passe par le pipeline standard `SheetsApi` (cache 5 min) et est chargé par `HomeComponent.chargerDonnees()` avec Restaurants/Activités/Magasins/Plats (passé en `@Input()` à `PlanningComponent`), pour profiter du même rafraîchissement forcé quel que soit l'onglet actif — en best-effort : une erreur sur cet onglet (`catchError` avant le `combineLatest`) n'empêche pas le chargement du reste des données. Cliquer sur le bandeau ouvre une popup de détail dédiée (adresse, dates+horaires de check-in/out, commentaires, lien Google Maps si renseigné) ; pas de lien vers la Carte ni d'ajout possible depuis "Ajouter un lieu" (hors périmètre v1).

## Ajouter un lieu (`components/ajout-lieu/`)

- Bouton "+" dans l'en-tête (visible sur toutes les vues) ouvre une modale bottom-sheet plein écran.
- Écrit **directement dans le Google Sheet** (pas de brouillon/validation intermédiaire) via l'API Sheets v4, authentifié avec le compte Google de l'utilisateur (OAuth2 côté navigateur, scope `spreadsheets`) — voir `docs/architecture-et-pieges.md` pour le détail du canal d'écriture et ses limites (token en mémoire, non persisté).
- Sélecteur de type (Restaurant / Activité / Magasin / **Plat** / **Quartier**), champs communs aux 3 lieux (Nom, Quartier, Lien, Localisation, Commentaires) + champs spécifiques par type (Description/Prix pour Restaurant et Activité, Vidéo/Menu pour Restaurant, Temps pour Activité, Type pour Magasin).
- **Plat** n'est pas un lieu : pas de Quartier/Localisation dans le formulaire, mais Catégorie (Plat/Snack, mêmes valeurs que `PlatCategory`) et Wiki/lien à la place. Écrit dans l'onglet de référence "Plats" (gid `2053739160`, `PlatService`), pas dans un onglet de lieu.
- **Quartier** non plus : ni Description/Prix/Commentaires ni les autres champs communs, juste Nom du quartier + Ville (chip parmi les villes déjà connues via `VilleService`, ou saisie manuellement pour une ville inédite). Écrit dans la feuille de référence "Quartiers" (gid `1855356526`, colonne `Mood` laissée vide). Si la ville tapée à la main ne correspond à aucune ville connue (comparaison insensible casse/accents), une confirmation est demandée ("Nouvelle ville ?", même schéma que `confirmerEcrasement()` pour Places) avant de l'ajouter à la feuille de référence "Villes" (gid `357846773`, `VilleService` — jusqu'ici injecté nulle part ailleurs dans l'app), pour éviter qu'une faute de frappe sur une ville existante crée un doublon silencieux dans le Sheet partagé ; annuler laisse le formulaire intact. Une fois confirmée (ou si la ville correspond à une ville existante), la ville est écrite en premier puis le quartier. Comme pour Plat, la modale reste ouverte après l'ajout et les listes de quartiers/villes sont rechargées aussitôt, donc un quartier (et sa ville, le cas échéant) tout juste créés apparaissent immédiatement dans le picker de quartier ci-dessous sans fermer/rouvrir la modale.
- Champ "Plats" du formulaire Restaurant : chips colorées (vert/rouge, même code que le badge du détail restaurant — `PlatService.getSeverity`), sélection/désélection au tap, alimentées par `PlatService.getPlats()`. Depuis que la modale reste ouverte après un ajout (voir ci-dessous), un plat tout juste créé via le type "Plat" apparaît directement dans cette liste sans avoir à fermer/rouvrir.
- Quartier (pour Restaurant/Activité/Magasin) choisi via un picker bottom-sheet groupé par ville, alimenté par la liste exhaustive de `QuartierService` (contrairement au picker de filtre de la Liste, qui ne connaît que les quartiers déjà présents dans les lieux chargés).
- Bouton unique "Remplir automatiquement"/"Identifier ce lieu avec l'IA" (Restaurant/Activité/Magasin, masqué en mode Franchise — `AjoutLieuComponent.remplirAutomatiquement()`) : remplace 4 anciens boutons séparés (Identifier IA / Google Places / Description IA / Plats IA) par un seul qui décide lui-même quels services appeler selon ce qui est déjà renseigné dans le formulaire, plutôt que de laisser l'utilisateur choisir le bon bouton dans le bon ordre.
  - **Pas encore de quartier connu** (y compris en mode édition, où quartier est toujours déjà renseigné, donc cette branche n'y est jamais prise) : interroge le backend IA (`IaService.rechercherLieu()`, endpoint `/ai/recherche-lieu` de ClaudeApiTkt) avec le Nom seul, le type de lieu et la liste des **villes** connues du voyage (`AjoutLieuComponent.villesConnues`, feuille de référence "Villes") — volontairement les villes et pas les quartiers déjà catalogués : demander à l'IA de se limiter aux quartiers déjà présents dans le Sheet la faisait presque toujours répondre "aucun résultat" dès que l'établissement n'était pas dans l'un de ces quelques quartiers précis, alors que donner juste la ville la laisse citer n'importe quel quartier réel de cette ville. Jusqu'à 5 suggestions sont retournées (nom, quartier, ville, courte raison), affichées en cartes cliquables (`AjoutLieuComponent.suggestionsIa`). Choisir une suggestion (`choisirSuggestionIa()`) préremplit Nom (repris exact) et Quartier (matché sur la liste connue de `QuartierService` si possible, sinon la valeur suggérée telle quelle, même si elle n'existe pas encore comme quartier de référence) puis enchaîne **automatiquement** sur la suite ci-dessous. Purement best-effort côté IA (résultats non garantis, pas d'écriture avant validation manuelle du formulaire) ; aucune suggestion trouvée affiche un message invitant à choisir un quartier manuellement (le bouton, rappuyé une fois un quartier choisi à la main, prend alors la branche suivante).
  - **Quartier déjà connu** (`AjoutLieuComponent.completerAutomatiquement()`) : enchaîne, en ne relançant que ce qui manque encore (pour ne pas écraser une valeur déjà saisie ni multiplier les appels réseau/popups de confirmation inutiles) —
    1. si Lien et Localisation sont tous deux vides : recherche l'établissement via Places API (New) à partir de Nom + Quartier, préremplit Lien (site web) et Localisation (badge "auto" sur les champs concernés, retiré dès que l'utilisateur les retouche à la main ; confirmation demandée si l'un des deux contient déjà une valeur). Pour un Restaurant, tente aussi de présélectionner des plats déjà connus dont le nom apparaît dans le résumé Google de l'établissement — best-effort, Places ne fournissant pas de vraie liste de plats, à vérifier avant d'ajouter. **Aperçu photo** : la première photo Google Places du résultat (si disponible) s'affiche au-dessus du message de résultat (`ResultatPlaces.photoUrl`, endpoint Photo media de Places API New, utilisable directement en `<img src>` sans appel HTTP intermédiaire côté app) — aide à vérifier que c'est la bonne enseigne avant d'ajouter, surtout pour les chaînes ambiguës (Daiso, Uniqlo...) avant de basculer en mode Franchise ;
    2. si Description est vide : génère une description via l'IA (`IaService.genererDescription()`), à partir de Nom/Type/Quartier et du résumé Google Places obtenu à l'étape précédente le cas échéant ;
    3. pour un Restaurant, si aucun plat n'est encore sélectionné : extrait des plats via l'IA (`IaService.extrairePlats()`) à partir du même résumé Google Places — les plats reconnus dans le référentiel `PlatService.getPlats()` sont ajoutés à la sélection, les autres affichés à part en texte (`platsSuggeresInconnus`, invite à les ajouter via le type "Plat" si pertinent).
  - Le libellé du bouton et son icône (spinner) reflètent l'étape en cours (identification / recherche Places / génération description / extraction plats) ; chaque étape garde son propre message d'erreur dismissable (identification, Places, description, plats) affiché indépendamment sous le bouton.
- Case "Franchise" (Restaurant et Magasin — konbini, chaînes... pas Activité) : dispense de choisir un quartier — à la soumission (après confirmation, voir plus bas), une recherche Google Places ("Nom quartier") est lancée séquentiellement pour chacun des quartiers connus de `QuartierService` (`AjoutLieuComponent.soumettreFranchise()`), et une ligne (restaurant ou magasin selon le type actif) est ajoutée pour chaque quartier où un résultat est trouvé (silencieusement ignoré sinon — une franchise n'a pas forcément une instance dans tous les quartiers). Localisation vient toujours du résultat Places (spécifique à l'instance de ce quartier) ; Lien ne reprend le site web Places que s'il existe (le champ Lien du formulaire est masqué et inutilisé en mode franchise). Description/Prix/Plats/Commentaires/Type de magasin saisis une fois sont dupliqués sur chaque ligne. Une barre de progression texte ("quartier X/Y, Z trouvés") s'affiche pendant l'opération, à la place du bouton unique "Remplir automatiquement" (masqué en mode franchise, voir ci-dessus) ; un message récapitule le nombre de quartiers où la franchise a été ajoutée une fois terminé.
  - **Déduplication** : les restaurants et magasins déjà présents dans le Sheet (chargés par `RestaurantService`/`MagasinService`, comme pour la Liste/Carte) sont indexés par type puis nom normalisé → Set de quartiers (`AjoutLieuComponent.quartiersParNomParType`, matching insensible casse/accents comme le reste du formulaire). Les quartiers où un lieu du même nom existe déjà pour le type actif sont exclus de la recherche Places (ni recherchés, ni réécrits) et affichés en indice sous la case Franchise dès que l'utilisateur tape un nom qui matche un lieu existant, avant même de soumettre — pour éviter de recréer des doublons si le même membre du groupe relance une recherche franchise sur une enseigne déjà partiellement ajoutée.
  - **Confirmation avant lancement** : `confirmerRechercheFranchise()` (même schéma d'alerte que `confirmerEcrasement()`/`confirmerNouvelleVille()`) annonce le nombre de recherches Places qui vont être lancées avant de démarrer — ce nombre pouvant être élevé (un par quartier connu), les recherches Places sont facturées au-delà d'un certain quota.
  - **Annulation en cours de route** : un bouton "Annuler" apparaît à côté de la barre de progression pendant la recherche (`AjoutLieuComponent.annulerFranchise()`, désabonnement de la souscription RxJS en cours). Les quartiers déjà traités avant l'annulation restent acquis (lignes déjà écrites dans le Sheet) ; seuls les quartiers restants ne sont pas recherchés.
- **Alerte doublon sur un ajout normal** (Restaurant/Magasin, pas Activité) : réutilise le même index `quartiersParNomParType` que la déduplication Franchise ci-dessus. Si le Nom + Quartier saisis correspondent à un lieu déjà présent dans le Sheet, une confirmation ("Déjà présent ?", `confirmerDoublonSiNecessaire()`) est demandée avant d'écrire — utile quand un membre du groupe ignore qu'un autre a déjà ajouté ce lieu à ce quartier. Annuler laisse le formulaire intact ; sans doublon détecté, l'écriture se fait directement sans alerte, comme avant.
- Un compte Google connecté à l'app mais sans accès Éditeur sur le Sheet peut se connecter mais pas écrire (erreur 403 explicite).
- Après un ajout réussi, **la modale reste ouverte** (formulaire vidé, même type sélectionné) pour enchaîner plusieurs ajouts sans la rouvrir à chaque fois ; un toast confirme chaque ajout. Fermeture manuelle via le bouton "×".
- Fermeture accidentelle de la modale (swipe, tap sur le fond, bouton "×") bloquée par une confirmation tant que le formulaire contient une saisie non vide (`AjoutLieuComponent.confirmerAbandon()`, appelé par `HomeComponent` via `[canDismiss]` sur la `ion-modal`).
- Messages d'erreur et de résultat de recherche Places sont dismissables (bouton "×" dédié) plutôt que de rester affichés jusqu'au prochain essai ; un texte d'aide sous le bouton "Ajouter au Sheet" explique pourquoi il est désactivé quand le formulaire est invalide.
- Après ajout réussi : toast de confirmation, fermeture de la modale, rechargement des données pour que le nouveau lieu/plat apparaisse immédiatement.
- Un magasin n'a qu'un seul quartier dans ce formulaire, comme le modèle de données (voir pièges connus) — un magasin avec plusieurs antennes doit avoir une ligne par quartier dans le Sheet (`scripts/dupliquer-quartiers.mjs` automatise cet éclatement pour les lignes existantes à virgules).

## Notes et Favoris (services)

- `FavorisService` (`Set<string>`) et `NotesService` (`Map<string,string>`), tous deux localStorage, **100% locaux à l'appareil** — pas de compte, pas de synchronisation entre les membres du groupe. Indexés par l'id de lieu généré par `genererIdLieu()` (`utils/lieu-id.ts`, nom + quartier normalisés) — voir `docs/architecture-et-pieges.md` pour le piège corrigé (ancien id basé sur la position dans le Sheet, instable dès qu'une ligne est ajoutée/supprimée par un autre membre du groupe).
- **Export/Import** (boutons dans l'en-tête, icônes téléchargement/upload) : `HomeComponent.exporterDonnees()` télécharge un fichier JSON (`{ version, exporteLe, favoris: string[], notes: Record<id,texte> }`) ; `onFichierImporte()` relit un tel fichier et fusionne son contenu via `FavorisService.importer()`/`NotesService.importer()`. Ces deux services étant 100% locaux (pas de compte), c'est le seul moyen de sauvegarder ou transférer favoris/notes entre appareils. L'import est non destructif par construction : les favoris importés s'ajoutent à l'existant (union), les notes importées ne remplacent jamais une note déjà présente sur l'appareil (évite qu'une restauration écrase une saisie plus récente).

## UX transverse

- Toasts de confirmation (favori ajouté/retiré, note enregistrée/supprimée) — reflètent l'échec réel si la sauvegarde localStorage échoue (quota dépassé, navigation privée), pas juste une confirmation optimiste.
- Thème clair/sombre (bouton dans l'en-tête) : suit la préférence système en direct pendant la session tant que l'utilisateur n'a jamais basculé le thème manuellement (`ThemeService`) ; dès qu'il le fait une fois, son choix explicite est mémorisé et n'est plus jamais écrasé par un changement système.
- Zones de tap ≥ 44px sur les filtres et boutons de section.
- Pull-to-refresh sur Liste/Favoris et sur Planning (pas sur Carte).
- **Swipe horizontal entre onglets** (`HomeComponent.onTouchStartContenu()`/`onTouchEndContenu()` sur `ion-content`, delta X franc ≥ 60px et delta Y faible ≤ 40px pour ne pas interférer avec le scroll vertical) : parcourt l'ordre Liste → Carte → Favoris → Planning en plus des taps sur la tab bar. Désactivé quand la vue active est la Carte (le geste doit rester réservé au pan Leaflet) et sur les rangées qui défilent elles-mêmes horizontalement (chips de filtres, "Vus récemment", mini-nav du Planning), pour ne pas changer d'onglet par erreur en les faisant défiler.
- Retour haptique léger (vibration ~15ms, `navigator.vibrate`) au tap sur favori ou sauvegarde de note — best-effort et silencieux si l'API n'est pas supportée (iOS Safari notamment).
- Petite animation "pop" (`favoriAnime`, ~300ms) sur le cœur au moment où un favori est basculé, carte de lieu comme popup détail — retour visuel plus marqué que le seul changement d'icône/couleur.
- Icône de rafraîchissement animée (rotation continue) pendant le chargement, plutôt que le seul bouton désactivé — feedback plus clair que "rien ne se passe".
- Fondu (`mask-image`) sur les bords gauche/droit des rangées scrollables horizontalement (chips de filtres, "Vus récemment", mini-nav de jours du Planning) : indice visuel qu'il y a plus de contenu à faire défiler. CSS dupliqué entre `home.component.scss` et `planning.component.scss` (encapsulation de vue Angular) ; reste visible même quand tout le contenu tient déjà à l'écran (pas de détection JS de dépassement, jugée inutile pour un effet aussi discret).
