# Architecture et pièges connus

Choses non évidentes en lisant juste le code — à vérifier avant de "corriger" quelque chose qui est en fait volontaire, et à ne pas re-casser.

## Modèle de données

- **`LieuAffichable`** (`models/lieu-affichable.model.ts`) unifie restaurant/activité/magasin pour l'affichage (Liste/Carte/Favoris). Construit dans `HomeComponent.chargerDonnees()` à partir des modèles bruts — les modèles bruts (`RestaurantModel`, `ActiviteModel`, `MagasinModel`) sont conservés à part (`restaurantsBruts` etc.) pour alimenter la popup de détail, qui a besoin de champs absents de `LieuAffichable` (Description, Avis, Plats...).
- **Piège corrigé — id de lieu basé sur l'index de ligne.** `RestaurantService`/`ActiviteService`/`MagasinService` généraient `id: type + '_' + index` (position dans le tableau après filtrage). Le Sheet étant édité collaborativement, l'insertion/suppression d'une ligne par un membre du groupe décalait silencieusement tous les index suivants — donc, au chargement suivant, les favoris/notes localStorage de tout le monde (indexés par cet id, voir `FavorisService`/`NotesService`) se retrouvaient attachés au mauvais lieu, sans erreur. Remplacé par `genererIdLieu()` (`utils/lieu-id.ts`), qui dérive l'id du nom + quartier normalisés — stable tant que ces deux champs ne changent pas, pas garanti unique à 100% (deux lieux identiques dans le même quartier collisionneraient) mais très robuste en pratique. **Effet de bord accepté** : ce changement change la valeur des ids existants, donc les favoris/notes déjà enregistrés par les utilisateurs avant ce fix ne matcheront plus rien après mise à jour (reset silencieux, pas de migration possible faute d'ancien mapping id→lieu fiable).
- **`QuartierModel.Ville`** est résolu via `resoudreQuartier()` (`utils/quartier.ts`), qui cherche dans la feuille de référence "Quartiers" (gid `1855356526`). Ne jamais recaster un `Quartier` brut du CSV directement en `QuartierModel` : le champ `Ville` ne serait pas peuplé.
- **Piège corrigé — coordonnées manquantes** : `RestaurantService`/`ActiviteService` construisent leurs objets par spread + cast TypeScript (`{...row, ...} as RestaurantModel`), **sans jamais appeler `new RestaurantModel(...)`**. Or c'est le *constructeur* de `RestaurantModel`/`ActiviteModel` qui calcule `latitude`/`longitude` à partir du lien Google Maps (`GeolocationService.extraireCoordonnees`). Résultat : ces deux services doivent recalculer les coordonnées **explicitement** dans le `.map()`, exactement comme le fait déjà `MagasinService`. Si un nouveau champ calculé est ajouté au constructeur d'un de ces modèles, il faut penser à faire pareil ici — le constructeur ne s'exécute jamais en pratique pour ces trois services.
- **`GeolocationService.extraireCoordonnees`** (et sa copie Node dans `scripts/lib/google-sheets.mjs`, à garder synchronisée) teste 3 formats de lien Google Maps, dans cet ordre précis :
  1. `!3d<lat>!4d<lng>` — position précise du lieu, prioritaire.
  2. `q=<lat>,<lng>` ou `query=<lat>,<lng>` — formats qu'on écrit nous-mêmes depuis l'app/les scripts de maintenance (voir ci-dessous).
  3. `@<lat>,<lng>` — centre de la vue au moment du partage, peut être décalé, donc vérifié en dernier.
- **Piège corrigé — lien "Localisation" sans fiche lieu au clic.** `PlacesSearchService` (app) et `fetch-localisation.mjs` (script) écrivaient `https://www.google.com/maps?q=<lat>,<lng>` : reconnu par `extraireCoordonnees` (donc le marqueur s'affichait bien sur la Carte de l'app), mais cliqué dans Google Maps ça n'ouvre qu'un pin sur des coordonnées, sans nom/avis/horaires/photos du lieu — Google Maps n'a pas de quoi savoir à quel établissement ce pin correspond. Corrigé en demandant en plus le champ `places.id` à Places API (New) et en écrivant `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>&query_place_id=<id>` (format "Search Action" documenté par Google Maps URLs) : le `query_place_id` fait que Google Maps affiche la fiche complète du lieu au clic. Repli sur l'ancien format `?q=<lat>,<lng>` si Places ne renvoie pas d'id (cas normalement inexistant pour un résultat valide). Les liens déjà écrits avant ce correctif restent au format `?q=`, toujours reconnus par `extraireCoordonnees` (donc pas cassés dans l'app) mais toujours sans fiche au clic — `fetch-localisation.mjs --reformater` permet de les retraiter a posteriori (bypass volontaire du cache, dont les entrées antérieures à ce correctif n'ont pas d'id). La construction du lien est maintenant partagée (`construireLienLocalisation()` dans `scripts/lib/google-sheets.mjs`) plutôt que dupliquée entre scripts, pour ne pas re-diverger.
  - **Piège corrigé — même défaut dans `dupliquer-quartiers.mjs`, en pire.** Ce script (qui éclate une ligne multi-quartiers en une ligne par quartier, voir plus bas) écrivait carrément le `googleMapsUri` **brut** renvoyé par Places — pas même le `?q=lat,lng` des deux autres. Un `googleMapsUri` est le plus souvent un lien par `cid` (`https://maps.google.com/?cid=...`), qu'aucun des 3 formats reconnus par `extraireCoordonnees` ne matche : les lignes issues d'un éclatement perdaient donc silencieusement `latitude`/`longitude` (pas de marqueur sur la Carte, pas de tri par distance), sans que rien ne le signale. Corrigé pour demander `places.id`/`places.location` (comme les deux autres) et construire le lien via `construireLienLocalisation()`. Comme pour `fetch-localisation.mjs`, une entrée en cache (`scripts/.cache/quartiers.json`) antérieure à ce correctif n'a pas de `location` exploitable : elle est automatiquement ignorée (sans besoin de `--rafraichir`) plutôt que de reconstruire un lien vide à partir d'elle.
- **Piège corrigé — `MagasinModel.Quartier` en tableau cassait le filtre par quartier.** `MagasinModel.Quartier` était un `QuartierModel[]` (pour représenter la colonne "Quartier" à virgules du Sheet — un même magasin pouvait avoir plusieurs antennes listées sur une seule ligne), mais `HomeComponent.chargerDonnees()` construisait `LieuAffichable.quartier` (singulier, comme pour Restaurant/Activité) à partir de `m.Quartier[0]` uniquement : un magasin listé "Shibuya, Shinjuku" n'apparaissait donc **jamais** en filtrant la Liste/Carte sur Shinjuku, ni dans le regroupement Ville→Quartier, alors que le popup détail affichait bien les deux badges une fois le magasin trouvé via Shibuya. Corrigé en alignant `MagasinModel.Quartier` sur `RestaurantModel`/`ActiviteModel` (un seul `QuartierModel`, plus un tableau) : `MagasinService` ne garde que le premier quartier d'une éventuelle colonne à virgules (`row.Quartier.split(',')[0]`) plutôt que de les résoudre tous. Un magasin avec plusieurs antennes doit désormais avoir une ligne par quartier dans le Sheet — c'est justement ce que fait `scripts/dupliquer-quartiers.mjs` (déjà existant, seul mécanisme prévu pour "diviser" une ligne multi-quartiers en plusieurs lignes mono-quartier, avec une recherche Places par antenne pour un lien Localisation propre à chacune).
- **`filtreActif`** (`HomeComponent`) défaut à `'tout'`, pas à `'restaurant'`. Ce filtre est partagé entre Liste et Carte (la Carte reçoit `lieuxAffiches()`, déjà filtré) : un défaut restrictif masquait silencieusement activités et magasins sur la carte tant qu'on n'avait pas cliqué un autre chip.
- **`Trajet`** et **`Free`** sont des valeurs spéciales de `ActiviteModel.Nom` (`NOMS_ACTIVITES_TECHNIQUES`, `HomeComponent.chargerDonnees()`) : des activités "techniques" (trajet entre deux villes, temps libre) sans intérêt à afficher comme un lieu. Exclues explicitement à la construction de `lieuxActivites` — donc absentes de la Liste, de la Carte, des Favoris, et du matching Planning→lieu (qui se base sur `lieux()`). Elles restent affichées normalement dans le Planning lui-même (onglet Sheet indépendant, `PlanningService`), juste sans lien cliquable vers une fiche lieu puisqu'elles n'existent pas dans `lieux()`.

## Planning : ville inférée, pas toujours lue directement

Dans le Sheet, la colonne "Ville" de l'onglet Planning n'est renseignée que sur certaines lignes (convention de cellules fusionnées côté Sheet ; l'export CSV laisse les autres lignes vides). Un simple "report de la dernière valeur non vide" est **incorrect** : certains séjours (ex: Kyoto, ou un deuxième passage à Tokyo) n'ont jamais de valeur explicite dans la colonne Ville sur toute leur durée, ce qui aurait attribué à tort ces activités à la ville précédente.

`PlanningService.parserCsv()` s'appuie donc sur la colonne "Trajet", qui contient systématiquement un texte du type "Trajet vers `<Ville>`" / "Vol vers `<Ville>`" à chaque changement de ville — y compris quand la colonne Ville elle-même est vide. La ligne de trajet appartient encore à l'ancienne ville ; c'est la ligne *suivante* qui bascule. Voir le commentaire en tête de `parserCsv()` pour le détail de l'algorithme.

Si le format du Sheet change (plus de "vers X" dans Trajet, ou une autre convention), cette inférence casse silencieusement — pas d'erreur, juste une mauvaise ville affichée.

## Deux pipelines de données indépendants

- `SheetsApi` (cache 5 min par gid, localStorage) alimente Restaurants/Activités/Magasins/Quartiers/Plats/Hébergements — chargés ensemble via `combineLatest` dans `HomeComponent.chargerDonnees()`, qui les passe à `PlanningComponent` via l'`@Input() hebergements` (même mécanisme que `[lieux]`). Choix délibéré malgré le fait que les hébergements ne servent qu'au Planning : les inclure dans ce `combineLatest` leur donne le même rafraîchissement forcé que les autres onglets quel que soit l'onglet actif au moment du clic sur "Rafraîchir" — les charger uniquement depuis `PlanningComponent.ngOnInit()` les aurait laissés périmés (cache SheetsApi 5 min non invalidé) tant que l'utilisateur ne revenait pas sur l'onglet Planning après un rafraîchissement déclenché ailleurs.
- **Piège évité — un onglet Hébergement cassé ne doit pas casser tout le chargement.** `combineLatest` propage la moindre erreur d'un de ses observables à tous les autres : sans précaution, un onglet "Hébergement" pas encore publié sur le web (ou un gid invalide) ferait échouer aussi Restaurants/Activités/Magasins/Plats, avec le message d'erreur générique de `chargerDonnees()`. L'observable de `HebergementService.getHebergements()` est donc explicitement `catchError`-é vers `of([])` avant d'entrer dans le `combineLatest` : une erreur sur cet onglet se traduit par "aucun hébergement affiché", jamais par une erreur de chargement globale.
- `PlanningService` a son **propre** cache localStorage (`planning_cache`, stale-while-revalidate) et sa propre logique de chargement, complètement indépendante de `SheetsApi`.
- Conséquence : le bouton de rafraîchissement de l'en-tête (`HomeComponent.rafraichir()`) doit savoir déléguer au bon pipeline selon l'onglet actif. Il utilise une `@ViewChild(PlanningComponent)` pour appeler `planningComponent.charger()` quand `vue() === 'planning'`, sinon il rafraîchit lui-même restaurants/activités/magasins/plats.

## Carte : composant permanent, jamais détruit

`CarteComponent` reste monté en permanence dans `home.component.html` (masqué via `[class.masquee]` → `visibility:hidden`), **jamais** via `@if`. Historique : le détruire/recréer à chaque changement d'onglet épuisait les contextes WebGL du navigateur ("WebGL context was lost"), reproductible sur plusieurs navigateurs sur la machine de dev. Après ça, la tuile vectorielle (MapLibre GL) a aussi été abandonnée au profit de tuiles **raster** (MapTiler à l'origine, puis Geoapify — voir plus bas) — plus de dépendance WebGL du tout, seule la persistance du composant était nécessaire mais les deux mesures ont été prises ensemble.

Implication pratique : les effects de `CarteComponent` (mise à jour des marqueurs, de la position) tournent en continu même quand l'onglet Carte n'est pas affiché, mais ne font rien tant que la carte Leaflet n'existe pas encore (`this.carte`/`this.groupeMarqueurs` restent `undefined`, chaque méthode fait un early-return).

**Initialisation différée au premier `actif=true`, pas au montage.** `ngAfterViewInit()` n'initialise plus la carte inconditionnellement : `CarteComponent.essayerInitialiser()` (gardé par le flag `carteInitialisee`) n'appelle `initialiserCarte()` — donc la création de la carte Leaflet et le premier chargement de tuiles — qu'au moment où l'input `actif` passe à `true` pour la première fois, càd quand l'utilisateur ouvre effectivement l'onglet Carte. Avant ce fix, la carte s'initialisait dès le montage du composant (donc au lancement de l'app, même pour un utilisateur qui ne visite jamais cet onglet) : sur un compte au quota limité, ça épuisait le quota mensuel avec des tuiles jamais vues par personne. Un seul essai automatique par montage (échec inclus, `carteInitialisee` reste `true` même en erreur) : les réactivations suivantes de l'onglet ne redéclenchent pas de nouvelle tentative, seul le bouton "Réessayer" de l'état d'erreur le fait.

**Piège corrigé — fond de carte MapTiler remplacé par Geoapify (quota gratuit trop vite atteint).** Le fond de carte était initialement MapTiler (style `streets-v2`, tuiles raster) : son quota gratuit (100k tuiles/mois) s'épuisait trop facilement malgré le fix ci-dessus. Remplacé par Geoapify (style `osm-bright`, `environment.geoapifyApiKey`), au quota gratuit nettement plus large (~360k tuiles/mois, 3000 crédits/jour à 0,25 crédit/tuile) — voir `CarteComponent.initialiserCarte()`. Choisi spécifiquement parmi les alternatives (OSM standard, CARTO Voyager/Positron, Stadia Maps, Thunderforest) parce qu'il sert des tuiles construites sur le **schéma OpenMapTiles** open-source, comme MapTiler : ce schéma calcule lui-même un champ `name:latin` (translittération des noms non-latins, ex. japonais) utilisé par défaut dans le style `osm-bright` — cette romanisation automatique des noms de lieux (essentielle pour un guide en français au Japon) n'est donc pas une fonctionnalité propriétaire MapTiler, contrairement à ce qu'on pourrait croire, et se retrouve chez tout hébergeur du même schéma. Les tuiles OSM standard ou CARTO Voyager/Positron n'offrent pas cette romanisation (noms dans la langue/l'écriture telle que taguée dans OSM, donc en japonais la plupart du temps) — écartées pour cette raison malgré un quota gratuit illimité ou plus généreux encore. Attribution "Powered by Geoapify" ajoutée à l'attribution Leaflet — exigence contractuelle du plan gratuit (retirée sur un plan payant), en plus des attributions OpenMapTiles/OpenStreetMap déjà présentes.

## Écriture dans le Sheet depuis l'app ("Ajouter un lieu")

Troisième canal de données, indépendant des deux précédents (lecture CSV publique via `SheetsApi`, et scripts Node en OAuth "Desktop app") : le bouton "+" de l'en-tête ouvre `AjoutLieuComponent`, qui écrit directement dans le vrai Google Sheet via l'API Sheets v4, authentifié en OAuth2 côté navigateur avec Google Identity Services (`GoogleAuthService`).

- **4 types, pas seulement des lieux.** `AjoutLieuComponent` gère aussi "Plat" en plus de Restaurant/Activité/Magasin — un plat n'a pas de Quartier/Localisation, il écrit dans l'onglet de référence "Plats" (gid `2053739160`, celui de `PlatService`) avec Catégorie (Plat/Snack) et Wiki. `TYPES_LIEU` distingue les 3 types "lieu" (Quartier obligatoire) de "plat" dans la validation du formulaire (`formValide`) et l'affichage conditionnel des champs.
- **OAuth2 identifie, il ne protège pas l'écriture.** Le droit d'écrire vient des permissions natives du Sheet (compte Google avec accès Éditeur) — l'API Sheets les applique elle-même. Un compte connecté à l'app mais sans droit d'édition sur le Sheet reçoit une 403 (`SheetsWriteService.messageErreur`).
- **Token en mémoire uniquement, pas de refresh token.** Contrairement au flow "Desktop app" des scripts (`scripts/lib/google-sheets.mjs`, refresh token persisté dans `token.json`), GIS côté navigateur ne fournit qu'un access token de courte durée (~1h), sans refresh token pour ce type de client. `GoogleAuthService.token` vit en mémoire (signal), jamais en localStorage.
- **Reconnexion silencieuse.** Pour éviter de redemander un clic "Se connecter" à chaque ouverture du formulaire, `GoogleAuthService` mémorise dans localStorage (`google_auth_deja_consenti`, un simple booléen — jamais le token) le fait que l'utilisateur a déjà accordé le scope une fois sur cet appareil, puis tente un `requestAccessToken({prompt: ''})` (`tenterReconnexionSilencieuse()`). Ça ne fonctionne que si la session Google du navigateur est toujours active ; sinon l'échec est silencieux (loggé en `console.warn` pour debug) et l'écran de connexion habituel reprend la main — pas de garantie que ça évite systématiquement une reconnexion (dépend de la session/cookies Google, pas d'un vrai refresh token).
  - **Piège — doit rester dans le geste utilisateur.** GIS n'a pas de mode "iframe silencieuse" comme l'ancienne gapi `auth2` : `requestAccessToken()` ouvre toujours un popup vers accounts.google.com en interne, même en mode `prompt: ''`. Un popup ouvert hors d'un vrai clic (ex: depuis `ngOnInit()` d'un composant qui vient de se monter, donc après coup) est bloqué par la plupart des navigateurs, sans erreur visible. `tenterReconnexionSilencieuse()` est donc appelée directement et de façon synchrone depuis le `(click)` du bouton "+" (`HomeComponent.ouvrirModaleAjout()`), jamais depuis `AjoutLieuComponent.ngOnInit()` (essayé en premier, ne fonctionnait pas pour cette raison).
- **Mapping colonnes lu dynamiquement, pas codé en dur.** `SheetsWriteService` résout le titre de l'onglet depuis le gid (`GET /v4/spreadsheets/{id}`), puis lit la ligne d'en-têtes de cet onglet pour construire une map nom de colonne → index avant de construire la ligne à ajouter. Même principe que `trouverTitreOnglet()`/`indexColonne()` dans `scripts/lib/google-sheets.mjs` — à garder cohérent si l'un des deux évolue (ex: nouvelle colonne, renommage). Cette map est mise en cache en mémoire par gid pour la durée de la session.
- Les colonnes de vote (`Valérian, Laurie, Greg, Alex, Mela, Tiffa, Tony, Fabrice`) et `Horaires` sont volontairement laissées vides par le formulaire d'ajout : `Horaires` est rempli plus tard par `fetch-horaires.mjs`, les votes sont saisis manuellement par chacun dans le Sheet.
- Après un ajout réussi, `SheetsApi.clearCache(gid)` est appelé puis `HomeComponent` recharge (`chargerDonnees(true)`) pour que le nouveau lieu apparaisse sans attendre l'expiration du cache 5 min.
- `environment.googleClientId` doit être un ID client OAuth type **"Application Web"** (pas "Desktop app", incompatible navigateur) — voir README.md > Configuration pour la procédure de création.
- **Préremplissage via Google Places** (`PlacesSearchService`, bouton "Rechercher sur Google Places") : même endpoint `places:searchText` que `scripts/fetch-localisation.mjs`/`fetch-menu.mjs`, mais appelé depuis le navigateur avec une clé API (`environment.placesApiKey`) distincte de `PLACES_API_KEY` (scripts) et **restreinte par origine HTTP**, pas par IP serveur. Places API (New) ne renvoie pas de liste de plats : le préremplissage des plats pour un Restaurant est un best-effort qui cherche les noms de plats déjà connus (`platsDisponibles`) dans le résumé Google (`editorialSummary`) de l'établissement, rien de plus fiable n'étant disponible côté Places.

**Piège corrigé — Leaflet + leaflet.markercluster en scripts globaux, pas en modules ES.** `leaflet.markercluster` est un plugin qui mute un `L` global déjà existant (`L.MarkerClusterGroup = ...`) plutôt que d'exporter proprement ses propres bindings. `import * as L from 'leaflet'; import 'leaflet.markercluster';` fonctionnait en dev (`ng serve`) mais plantait en build de production avec `TypeError: L.markerClusterGroup is not a function` — le bundling ESM/CJS de production ne garantit pas que ce plugin s'exécute au bon moment pour retrouver le `L` importé par le composant. Fix : les deux libs sont chargées en scripts globaux classiques (`angular.json` > `build` > `options` > `scripts`, dans cet ordre : `leaflet.js` puis `leaflet.markercluster.js`), qui s'exécutent avant le bundle Angular et posent un vrai `window.L` sans ambiguïté de bundler. Côté `carte.component.ts`, plus aucun import runtime de `leaflet`/`leaflet.markercluster` : uniquement `import type * as LeafletType from 'leaflet'` (typage, zéro JS émis) + `/// <reference types="leaflet.markercluster" />` (augmentation de types) + `const L: typeof LeafletType = (globalThis as ...).L;` (lit la vraie valeur sur le global posé par les scripts). Un fichier TS étant un module, il ne peut pas référencer un "UMD global" par son nom nu (`export as namespace L` de `@types/leaflet`) sans ce détour — d'où cette construction en apparence indirecte.

## Eki stamps : donnée statique générée une fois, pas un pipeline Sheet

La couche "Eki stamps" de `CarteComponent` (voir `docs/fonctionnalites.md` > Carte) n'est **pas** alimentée par `SheetsApi` : ces ~1600 points (carnet de tampons de gares/lieux touristiques, source externe `stamp.funakiya.com`) viennent de `EKI_STAMPS_itineraire_FR.kmz` (à la racine du repo), converti une fois en JSON par `scripts/generer-eki-stamps.mjs` vers `public/eki-stamps.json`, servi tel quel comme asset statique (`provideHttpClient()` + `EkiStampService.getEkiStamps()`, `shareReplay(1)`).

- **Pas de synchronisation automatique.** Modifier le KMZ (ajouter une zone, corriger un nom) nécessite de relancer `node scripts/generer-eki-stamps.mjs` puis de rebuild/redéployer l'app — contrairement aux lieux du Sheet (cache 5 min, rafraîchissement à la demande), ce fichier ne change jamais entre deux déploiements.
- **`adm-zip`** (devDependency) est utilisé uniquement par ce script pour décompresser le KMZ (qui est un zip) en Node — jamais importé côté app.
- **Ancienne approche abandonnée : onglet "Tampon" avec iframe Google My Maps.** Une première version affichait ces points via un `<iframe>` pointant vers une carte Google My Maps (créée en y important le même KMZ), dans un onglet séparé. Problème : fond de carte différent de celui de `CarteComponent` (tuiles Google vs celui, raster, de `CarteComponent`) et carte totalement statique (My Maps ne se resynchronise pas avec le KMZ, pas de filtres). Remplacé par l'intégration directe en tant que mode dédié de `CarteComponent` (même fond de carte, clustering, marqueurs emoji comme les lieux) — voir `CarteComponent.basculerModeCarte()`.

## Scripts de maintenance (`scripts/*.mjs`)

Indépendants de l'app, authentification OAuth "Desktop app" (pas de compte de service — bloqué par `iam.disableServiceAccountKeyCreation` sur un compte Google managé par une organisation ; utiliser un compte personnel si besoin). Détails d'usage complets dans `README.md`.

- Les 3 scripts qui appellent Places API partagent un cache disque (`scripts/lib/cache.mjs`, fichiers sous `scripts/.cache/`, gitignorés) par `(feuille, nom, quartier)`, pour économiser les appels API et garantir que ce qui est écrit avec `--appliquer` correspond exactement à ce qui a été vu à l'aperçu.
- Le lien Google Maps écrit par les scripts est toujours construit nous-mêmes (jamais le `googleMapsUri` brut de Google, souvent un lien par `cid` sans coordonnées lisibles), au format `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>&query_place_id=<id>` — reconnu par `extraireCoordonnees` côté app, et affiche la fiche complète du lieu au clic dans Google Maps grâce à `query_place_id` (voir le piège "lien Localisation sans fiche lieu au clic" plus haut).

### Port Java (menu caché "jobs") — pas un remplacement, un second consommateur

Ces 4 scripts existent aussi en version Java côté backend ClaudeApiTkt (package `jobs/`, voir son `CLAUDE.md`), pour permettre au menu caché de l'app (`JobsPanelComponent`) de les déclencher en prod. **Les fichiers `.mjs` restent la référence** : ce sont eux qu'on édite pour changer le comportement d'un job (colonnes, gids, format des liens/horaires...), le port Java doit ensuite être répercuté à la main (pas de génération automatique). Deux écarts assumés par rapport aux scripts :

- **Auth sans flow OAuth interactif.** Un serveur headless ne peut pas ouvrir de navigateur pour le flow "Desktop app". Le port Java réutilise directement le `refresh_token` déjà présent dans le `token.json` généré une fois par un script Node (voir `GoogleSheetsConfig` côté ClaudeApiTkt) — remplacer ce refresh token périmé (révoqué, changement de compte Google) est une opération manuelle sur le host de déploiement, pas quelque chose que l'app peut re-déclencher elle-même.
- **Cache mémoire (Caffeine) au lieu du cache disque** (`scripts/.cache/*.json`) : le serveur Java est un processus long-vivant (contrairement aux scripts Node relancés à chaque exécution), un cache en mémoire suffit et évite de gérer un volume disque partagé entre requêtes concurrentes.

**Suivi de progression en polling, pas en SSE.** Le backend ClaudeApiTkt est 100% servlet-bloquant (pas de `SseEmitter`/WebFlux dans ce repo) et le relais same-origin (`public/api/jobs.php`) est un simple curl PHP sans streaming chunk-par-chunk. Plutôt que d'ajouter cette complexité pour un outil de maintenance interne, `JobsPanelComponent` sonde `/jobs/etat` toutes les 1,5s avec un curseur incrémental (`depuis`/`total`) — perçu comme "en direct" sans les fragilités d'un vrai stream à travers PHP.

## Conventions de code

- Tout le code (variables, commentaires, messages UI) est en **français**.
- Angular 21 standalone + signals + zoneless : pas de `NgModule`, pas de `Zone.js`, nouvelle syntaxe de contrôle de flux (`@if`/`@for`/`@let`).
- Pas de routing Angular : la navigation entre onglets est un simple signal (`vue`), pas d'URL dédiée par onglet.
